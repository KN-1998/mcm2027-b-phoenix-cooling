# 合同写法模板（A 题实践过，可直接套到 B）

> 两个文件：`MODEL_SPEC.md`（要建什么）与 `CODER_SPEC.md`（怎么算、怎么验）。
> 经验：**写得像可执行规格，而不是论文提纲。**

## 一、MODEL_SPEC 骨架

### 1. 符号表（必带单位与来源类型）

| 符号 | 定义 | 单位 | 类型 |
|---|---|---|---|
| … | … | … | OBS / MODEL / ASSUME |

- `OBS` = 公开观测（必须有 URL + 页码/表号 + 核验级别）
- `MODEL` = 由公式导出
- `ASSUME` = 明确假设，必须有测试范围

> B 题对应：`d_i` 需求（visits/day）、`t_ij` 行程时间、`c_j` 站点容量、`b` 预算、`w_i` 脆弱性权重。

### 2. 状态量之间的换算（防混用）

A 题曾把"岸线位置 / 滩宽 / 沙量"混用，被专家点名。B 题同样有三组易混：
- **visitor-visits/day ≠ 同时在场人数 ≠ 独立服务人数**（题面明确点出）
- **hydration station ≠ cooling center**（服务类型不可互换）
- **记录的死亡/发病 ≠ 某设施的因果效应**

写一节"这些量不可互换"，并把换算关系显式写出。

### 3. 方程 / 模型定义 + 口径

每个建模选择写清"选了哪个、为什么不选另一个、代价是什么"。A 题的教训：
双计数口径选了保守的那个，就要**明写"这是保守上界，实测只有 X%"**，否则会被当成错误。

### 4. 参数表

| 参数 | 基线 | 范围 | 类型 | 证据 id |
|---|---|---|---|---|

`evidence id` 指向 `ledger/claims.csv`，**每条都必须能追到来源或明确标 ASSUME**。

### 5. 决策记录 D1…Dn

每条：日期 / 裁决 / 理由 / 影响面。**用于事后解释"为什么这样做"，也是答辩弹药。**

### 6. 结果 schema（固定键）

提前定死 `results.json` 的字段名，下游的审计脚本、图表脚本、论文表格都靠它。

## 二、CODER_SPEC 骨架

1. **§0 第一小时**：五步照抄清单（跑参考原型 → 开分支 → 建骨架 → 三条断言 → 第一个结果）
2. **§0.6 冲突裁决权**：文档矛盾时按"守恒 > 可执行 > 保守"自裁，记一行 `[自决]`，不停工
3. **验收判据 T1…Tn**：每条给"判据 / 参考实现实测值 / 容差"
4. **口径陷阱清单**：把已知的坑写成"不要这样写"，附反例
5. **结果 schema + 台账恒等式**：一行公式，可逐行核

## 三、A 题那套测试分类（B 题照搬改）

| 类 | A 题例子 | B 题对应 |
|---|---|---|
| 守恒/恒等 | 沙量闭合 < 1e-6 | 覆盖/分配一致性：所有需求分配量 = 服务量 |
| 零输入 | 零源项保持常值 | 零需求 ⇒ 零部署、零成本 |
| 解析基准 | 对 erf 解收敛 | 对 p-median 小算例穷举最优 |
| 边界/极端 | 上限饱和 | 容量上限饱和、预算用尽 |
| 复现 | 同 seed 字节一致 | 同 seed 同解 |
| 指标口径 | 删失语义 | 公平性指标（Gini / 最差区比值）定义一致 |
