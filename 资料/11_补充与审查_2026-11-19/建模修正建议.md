# Q3/Q4 可直接执行的修正建议

审查版本：`c506b539fa61ac57b04fb822c8557e1cf3b003de`，2026-11-18。本备忘针对动态部署和中断响应；不把示例反例数值当作 Phoenix 观测数据。

当前已有实质修复：已部署设备故障的典型情景会将车队减为 p−1；故障设备不再作为迁出来源；搭建时间不再重复加；串行队列的等待进入开业时刻折减；超期限的候选方案不再计入可执行收益。Q3 的实际迁移小时已经进入 DP，主 pipeline 和独立 Q3 runner 也共用 `solve_week_dp`。这些修复应保留。

## 先改三项会直接改变结论的逻辑

### 1. 将车辆 ID 与站点 ID 拆开

`MCH-3` 当前既表示候选点又被当作车辆。这样即使该点根本没部署设备，`down_vehicle="MCH-1"` 仍会减一台车；真正设备故障时，又把该地点一并禁止其他健康设备使用。

引入 `vehicle_id -> current_site_id` 的显式部署表。设备故障只令相应车辆不可用；场地故障只令该场地不可提供服务。若损坏设备阻挡场地，作为另一个明确情景处理，不能默认绑定。

可采用以下约束，其中 `z[v,j,t]` 表示车辆 v 在时间 t 已到达并可在 j 服务：

- 每台车至多在一个地点：`sum_j z[v,j,t] <= healthy[v,t]`。
- 关闭地点不可服务：`z[v,j,t] <= site_available[j,t]`。
- 同一候选点只容纳一台车时：`sum_v z[v,j,t] <= 1`。
- `healthy=0` 的车辆直到显式维修/替换完成前不得重新服务；备用车、维修及运输都要单独计费计时。

故障接口必须核验 ID 属于当前实际部署车辆。压力测试的设备故障应从这份实际车辆表抽样；未知或未部署 ID 应拒绝并说明原因。场地故障则可抽固定设施或候选场地，两者的抽样总体要分别记录。

验收反例：默认 p=3 部署3/7/8，未部署的候选点1不能使车队变为2。当前代码在零搬迁、零耗时下产生 −21.252 人次/日“响应收益”，恰与压力测试 P10 对应，不能解释为搬迁停服成本。

### 2. 按响应后净服务选择方案，强制包含不搬

目前 `plan_response` 先取不扣迁移损失的静态最优点集，随后才安排路径、扣容量。应把“具体车辆分配、迁移、开业时间后的未满足需求”作为比较目标。

对当前8个点、p<=3的小规模，建议直接枚举：

1. 保留当前健康部署作为不搬候选；关闭场地上的设备可以停止服务，不凭空损失健康设备。
2. 枚举每个合法目标点集；对健康车辆与目标点的对应关系枚举精确匹配，不使用最近点贪心作为最优性依据。
3. 在人员/运输资源假设下计算具体就绪时间，先剔除违反响应期限的调度。
4. 依据就绪时间重算分时可服务容量，再调用同一分配 LP。
5. 在可执行方案中最小化 `未满足需求 + 搬迁成本权重×搬迁成本`；如需公平约束，始终使用相同的日公平口径。

应同时报告不搬未满足量、最优可执行未满足量、净收益和搬迁次数。若只比较未满足需求且不搬可行，所选方案的净服务收益不应为负。可以保留负收益动作作为被拒绝的候选，用于解释为什么不该搬。

当前独立反例：A→B需要1.5小时，健康车队均为1，冲击后不搬未满足127.938，静态选点后再扣迁移得到129.925，代码仍选择B并给出−1.987收益。该结果只能说明动作B被不搬支配，不能称最优响应。

### 3. 设备故障不应直接推出“搬迁无法恢复损失”

默认数据中设备在候选点3故障时，当前函数禁用点3，给出响应收益0。若仅设备坏而地点可用，健康车7搬到点3，另一台健康车仍在8，同样只有2台健康车；按当前时间代理耗时0.87小时，未满足量262.520→248.547，改善13.973人次/日。这里没有复活故障车。

因此需重算设备故障情景，并将结论写成条件判断：当故障地点仍可用、健康设备有剩余容量且搬迁净收益为正时，重排健康车队可能恢复部分服务；不会自动恢复故障设备本身的容量。

## 时间与人员约束怎样接入

### 4. 明确并行还是串行资源

若每台设备都有独立司机和搭建班组，可同时出发，响应完成时间是各车就绪时间的最大值。若只有一个共享班组，需要排队，并记录班组在车辆/场地之间的移动，不能仅把几段车程相加就视为完整人员调度。

统一拆出 `travel_hours`、`setup_hours`、`ready_time`：`arrive=depart+travel`，`ready=arrive+setup`。当前 `move_time_hours` 已含0.5小时搭建；如继续使用，不应再加第二遍，但输出列应称“行程及搭建合计”，避免将到达和开业都写成相同时刻而仍标成纯行车时间。

24小时为硬约束时，目标点集和调度顺序应在期限约束内一起选择。不能只让一个不合期限的静态目标返回False，便忽略其他可执行方案。

### 5. 用就绪时刻与营业时段的交集算容量

当前Q3/Q4仍把全日日容量乘一个折减系数，然后按原营业窗口分配到白天/晚间/夜间。这是日比例近似，不能同时宣称它已经给出满足全部时间约束的逐时调度。

推荐先定义每台设备吞吐率 q（人次/小时，来源或假设应明确），再按各时段 h 的实际可服务长度计算：

`capacity[v,j,h] = q[v,j] × length(period_h ∩ site_open_window_j ∩ [ready_v, close_v])`。

迁入前的时段容量必须为0，夜间营业需用绝对时间展开跨午夜区间。真实接待周转率和单站日容量缺失时，继续作为敏感参数，不从“170人同时容量”直接换算日人次。

### 6. 跨天行程必须保留在途状态

当前 DP 仅在搬迁当天扣至多10小时，次日只要目标点相同就恢复全容量。独立3日边界反例中，48小时搬迁从day1启动，day2已在目的地服务200人次，得到虚假的100人次动态改善。该例用于验证物理边界，不是声称 Phoenix 点对实际相距48小时。

可选实现：将车辆状态扩为“地点、是否在途、目的地、绝对就绪时刻”；到达之前所有后续时段容量为0。若暂不做跨天运输，则显式限制所有移动必须在允许窗口内完成，超过窗口的转移直接不可行，并对道路/公交中断单独说明适用范围。

Q3当前还会剪枝至逐日top-k点集的并集；8选3至多56种，建议提供全状态对照，或将结果明确称为剪枝DP结果。候选点之间的车辆匹配也应精确枚举。

## 接口与验收

### 7. 将主流水线的Q4与闭环实验对齐

主 `run_pipeline.py` 仍调用 `run_disruption`；它返回 `response_hours_assumed=24`、`response_hours_modeled=false`，只做停站后的静态重选，并未调用新的 `plan_response`。这可以保留为静态冲击基准，但主报告的24小时响应表必须调用修正后的闭环函数，并保留车辆、路线、时段容量与期限结果。

当前Q4 CLI在超期限时还会用浮点格式打印None，触发TypeError。对不可执行收益显示 `NA` 并保留原因；正常写完结果后以成功退出，或用明确且预先约定的状态码表示“情景不可行”。

建议最小验收集：

- 未部署车辆ID不改变健康车队；真实设备故障减一且从不作为迁出来源。
- 场地关闭保留健康车辆；设备故障保留未损坏场地的使用资格。
- 不搬可行时，服务目标下的最优可执行净收益>=0。
- 一条路线超期限而另一条可行时，应选择可行路线；全体不可行时明确报告。
- 串行与并行的就绪时间分别符合人员资源约束。
- 迁入前零服务；跨日未到达时持续零服务。
- 主pipeline与独立Q4 runner使用相同情景、同一闭环函数和相同输出结构。
- CLI以0.1小时预算触发不可行时仍能正确输出并完成。

完成这些修正后，重跑Q4场景表和压力测试，再更新“故障后是否值得搬”“负收益来自哪里”“24小时响应率”等政策表述。README中D05×2的Q3旧表在本轮最新代码下已复现同值（13.90/七日），因此仅凭旧metadata不能断定其数值已错；仍应重建可追溯记录。
