# 七问讲解与复算卡

供用户独立核实、练习，再与队员交流。它不是三人已掌握或已经答辩的记录，也不是要求背诵的成品答案。先不看下方讲解口述，再用文件复算；说不清的地方记录问题并回到原件、公式或代码。所有正式数字以`results/completion_20261121/`冻结文件为准。

## 1. 到底计算什么，现场怎样测？

**一句话。** 主模型在给定需求和供给假设下分配室内降温服务人次，并计算未满足的规划人次；不是预测死亡，也不是计算独立居民覆盖率。

\(D\)是需求人次，\(x\)是分配服务人次，\(U=D-\sum x\)是规划缺口。一个人重复来访可贡献多个人次；“同时在场人数”又需要停留/席位数据，不能由日访问上限直接换算。hydration只饮水，不作为室内空调供给。

主模型服务日为09点至次日09点，实证子模型却使用官方完整报告周的已实现intake次数，两者单位和目标不同。周到访是已经来到某站的人次，受开门、容量、选择和记录影响，不包括所有想来却没有来/被拒绝的人。

**怎么核。** 查`base/core/district_gap.csv`的`demand_visits/p3_unmet`，再查`empirical/weekly_observations.csv`的`jackson_visits/days`。解释为什么后者不能直接均分给12区。现场要分别记录到访、拒绝、排队、未到访障碍、重复口径、开门和配员，才能补主需求识别。

**临场变化。** 若评委把目标改为“独立居民获益”，先说明现在不能回答，需要去重和来源区数据；不能将本模型输出改个列名。

## 2. 如何从机制推到M1—M6？

用五分钟白板沿同一条链走：

1. **M1人次账本**：每个区/日/时段的需求等于已分配加未满足，\(D=\sum x+U\)。正负号来自定义，所有项同单位。
2. **M2可用出口**：假设原开业窗长度L、日容量C，吞吐率为C/L人次/小时；可用容量是该率乘“营业、时段、服务日、到达以后、配员允许”的交集小时数。停电/无许可/不可进入时供给为0，未知确认不自动当实测已确认。
3. **M3选址分配**：不可达或非室内边不允许x；每站每时段不能超供给、每区不能超需求。枚举候选组合，每组合求联合时段LP；再按日未满足率做公平约束或max-min。
4. **M4跨日**：状态是当天部署集合；转移包含逐车匹配和到达，送回M2求当天缺口，DP累加并留回溯。初日就绪，同日在途；超过24小时的运输被拒绝，而非次日自动恢复满服务。
5. **M5事故**：同一事故、需求和交通输入下比较不搬与重调度。关站影响位置供给，坏车减少健康车，不能混成一件事；串行和并行按实际团队条件区分。
6. **M6资产/资金**：拥有\(O\)、购买\(b\)、在用\(A\)分别记，\(O'=O+b,\ A\le O'\)，年度采购和全部在用运维/合同均计预算。停运仍持有，可买了暂不开，初始购置沉没。

**可手算的时钟例。** 一站9—22、日容量130，率10人次/小时。10点才到，则白天容量70、晚间50。不要给所有时段都乘\(1-1/10\)：晚间窗口完全没有损失。若人员只到17点，晚间是0，不能把日容量重新分配成白天130。日期日历要用次日早晨，不能把今天08—09当成今晚后的08—09。

**看哪里。** `MODEL_CHAIN.md`与`TECHNICAL_DERIVATION_20261121.md`；`tests/test_takeover_core.py`、`test_operational_completion.py`。最大流/割证书对拍与状态充分性证明负责数学正确性，不能据此声称现实会照模型运行。

## 3. 哪些有来源，哪些自推，哪些是假设？

**可核来源。** 官方周PDF给同站已实现访问；NOAA给机场日气温；城市运营刊物给2026地址、时段与季节；GTFS给历史发布班次；官方人口表给相应年份/地域统计。它们各自只支持自己的字段。

**自推/改造。** 服务账本、窗口容量、带容量和日公平的LP、日状态/库存DP由本题约束连续建立。经典MCLP与DP文献是方法家族背景，不能用一本书的题录冒充所有本地参数和推导已经被验证。具体读过什么见独立审查文件。

**仍是假设。** 12区代表点、潜在需求份额、未知站日容量、匀速吞吐、步行绕行与速度、最大等待政策、人员与采购价格、零交货期/储存等。500/200固定站容量是工作情景；Census坐标是地址插值，非入口实测。

**反证促成的改变。** 官方Jackson训练周有3304次访问，7天内至少一天不少于472。若把真实Jackson当成绝对每天50或120上限就矛盾；但这个下界不能赋给所有固定站、合成R01或MCH。Cholla MAG登记17点与官方热季21点冲突，故保留原表并显式增加官方运营层；不再说“同源字段重建正确所以供给现实正确”。

**怎么核。** 打开Week8原PDF第2页，再看`empirical/capacity_reconciliation.csv`及`source_operating_corrections.json`。说明为什么Mon-Sat开门时刻仍可能单独来自MAG，而不是官方“直到21点”这句话已经给了开门时间。

## 4. 如何用真实数据检验，比简单方法好在哪里？

**实际做法。** 只检验Jackson同站周已实现访问：20完整周，12周训练、4周开发选择、4周锁定测试。3天和10天的端点期间保留原件但不参加主要比较。直接读weekly列，不靠累计差分制造周观察。

固定四个候选：上一周、前四周均值、非负AR1、AR1加上一周热项。复杂候选必须比最佳简单基线降低至少5%开发MAE，实际没有达到，故退回四周均值。测试不用来选模型，天气也只用上一周。每过一周可用已过去的实际记录更新历史，所以它是滚动一步检验，不是开始时一次预测未来四周。

**怎么核。** 查`empirical/summary.json`的`development_scores/selected_model/test_scores/coefficients`，逐行重算`predictions.csv`中预测减观测的绝对值和平方。正式数据中的测试MAE和与上一周差额由该文件给出；不能只看图说“拟合很好”。检索曾看到一个测试周值、报告真正发布时间未知、测试只有4个相关周，均已披露。因此这是有边界的回顾性结果检验，不能说前瞻全盲或部署精度认证。

**没验证的量。** 12区潜在需求、未到访者空间分布、MCH吞吐率、全网实际覆盖、健康效果仍没有对应独立目标。补上真实周结果，不能自动替这些项目勾“通过”。

## 5. 哪个关键假设失败会改变结论？

不要回答“模型很稳健”。给一个具体输入、可行集和翻转。

**共同倍率反例。** 两区A/B，第0日需求100/75，第1日500/375，比例保持不变且共同乘5。A有固定站日容量50，移动站容量250，均9—17，各区只能到本区站；混合份额u=.5使白天需求占.425。固定站两日分别服务42.5和50。移动站初日在B服务31.875；第二日迁到A，扣.53小时后容量仍足，服务162.5。总需求1050，动态缺口763.125；最佳固定B缺口766.250，搬迁收益3.125。

原因不是空间需求比例改变，而是**固定供给没有随着需求放大**，剩余缺口排序能改变。故“同一倍率必无搬迁价值”是错误的一般命题；默认实际数据跑出零收益仅是那一次条件结果。独立复算：`tests/test_completion_invariants.py::test_common_demand_scaling_can_make_relocation_useful`。

**交通结构反例。** 将固定/候选站、需求、容量、时段、阈值全部保持，只把距离速度代理换成指定日期GTFS，选址可能变化。对照看`gtfs_registered/matched_inventory_siting.csv`或城市运营层的`gtfs_city/`，不能混用两个库存层来解释差异。

**排班范围。** 有日期的旅程处理班次、上下车、换乘、24点以上时刻，仍含接入/末段步行代理、有限登车/时限，以及非exact频率的明确等待政策。它是scheduled travel，不是实测OD；三个出发时刻的中位数不是旅行时间概率分布。

## 6. 随机一个数，如何从原件复算到正文？

**最小19人次例。** A需求10，可到S1/S2；B需求9，只能到S1；两站各容量10。若先把A全给最近S1，B被阻塞，只服务10。可行最优是B→S1取9、A→S2取10，总19；需求总量本身给出19上界，所以达到上界即证最优。

打开`base/core/minimal_case.json`看输入/LP/greedy，`minimal_case_flows.csv`看每条分配。LP也可能返回另一条达到19的同优流，不要求逐格完全等于某一手算流。检查需求/容量上限、总量和U，而不是只比较函数是否返回成功。

**再挑一个真实数。** Week8原PDF的3304是周已实现访问，导出到`empirical/weekly_observations.csv`；求3304/7得到472的平均及至少某日下界，但不能当日上限。若挑预测，按前四个已经结束的周取均值，再用目标周记录算误差；不要把目标周放进均值。

**再挑一条旅程或预算。** `gtfs_city/itineraries.json`按区、站、出发时刻找旅程，再对`independent_source_leg_audits.json`和原zip核trip/站序/时钟，分钟与秒先统一。Q5从plan行验证`owned_before+buy=owned`、`active≤owned`、`idled=owned-active`及采购+运维+合同是否等于total_cost、是否≤budget。配置、源提交与字段要追到对应run_meta，不能拿旧包的数字佐证新规则。

## 7. 最大失败是什么，因此实际改了什么？

本轮最大的证据缺口是曾有真实站点和官方引用，却不足以支持真实需求/覆盖预测。还发现：MAG遗漏主要项目且登记时段与运营公告不同；复杂周预测器没有胜过简单基线；共同倍率的零搬迁一般论断被反例推翻。这些不能靠更多图、MC次数或“limitations”消除。

实际动作是补同站周真实结果、按时间留出并退回简单基线；增加带来源的官方运营层；完善scheduledGTFS旅程；增加许可/供电/配员门控及成本包络；撤回错误命题并加入独立反例；将五年预知最优与非预知稳健计划分开报告。仍缺的现场数据以明确参数、范围、条件结论和下一步测量处理，不编成“已实证”。

**怎样解释robust与oracle。** Oracle预先知道完整热路径，是可行行动集合内的理想规划基准。Rolling按当前年信息逐年改；robust事先对各年可能热倍率集合选择一条共享行动序列，不用随后实现的热来切换动作。主目标为`min Σ_year max_heat unmet`，矩形集合允许逐年换最坏路径标签，所以它上界每条所供完整路径的缺口，不是只对三条命名路径做minimax，也不是经验概率置信集。公平次项取独立最坏率上界，可能不和总缺口的最坏热实现相同。

看`operations/nonanticipative_plan_comparison.csv`及`robust_plan_details.json`：同一行动在每条路径的实际评分与保守上界分开。差异包含信息集和目标差异，不能全部归功于“算法更先进”。`operating_days=1`时五年总分是五个代表日，不是五年真实总访客；工资/用电/耗材范围也不是当地MCH已签报价。
