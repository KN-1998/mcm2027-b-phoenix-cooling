# Q3与时钟容量的独立实现复核

日期：2026-11-20。实现负责人为主代理；本项复核人为Q4子代理（AI agent）。这是不同实现角色之间的复核，**不是人类队友签字或实证验证**。本代理也实现了Q4，故Q4专用测试属于作者自查；主代理仍须复核Q4。

## 复核问题与判定

Q3的状态是否足以表达实际声称的行动范围？在每天09:00开始并行搬迁、所有旅行与布置不超过24h、初始部署已就绪且站点/车辆同质的限制下，前一天完整点集就是下一日需要的状态。程序明确拒绝48h旅行，撤回了旧模型中“次日尚在路上却已满容量服务”的隐含假设。跨日旅行若要纳入，必须增加每辆车的在途位置/剩余时间，不能只把时间截断。

DP是否漏掉公共站点车辆交换？代码对前日全部车辆与当日目标点的全部双射枚举，允许A→B、B→C，未把公共点B固定为留驻。每条转换在给定就绪时间下用同一时段分配LP。固定点集在整周持续留驻的方案保留在候选中，因此动态最优未满足量应不高于周静态最优未满足量；测试以**未满足量**方向检查此不等式。

“optimal_within_model”是否过强？`top_k=0`对全部点集使用DP，结合上述完整匹配和合法gross下界，能最小化该有限模型的**全周未满足总量**。它没有全周最少搬迁次数或最小工时的最优性证书，也没有现实需求/行程的准确性证书。`top_k>0`明确标为`restricted_state_heuristic`；即使某个小例子的并集恰好等于全部状态，也保守保留此标记。

## 边界与时钟几何

专用测试还检查：48h旅行明确拒绝；每日同一需求时存在无搬迁且与静态相同的最优方案；top-K模式如实标记；10:00就绪只损失日间1小时，不损失17:00以后的容量；`capacity_is_explicit=True`的0容量不恢复为CLI默认250；周一08–17且周二关闭时，服务日周一09→周二09的夜间容量为0，若周二08–17开放则为10人次。

对无日历的所有整数开/闭时刻0..24，排除相等时刻后600种窗口，逐一比较3时段：`capacity_after_ready(...ready=0)`与原始`capacity_in_period`共1800项，最大绝对差1.4210854715202004e-14人次。只说明两个区间实现的无停服几何一致。

审查时发现并修复/推动修复两项：

1. 显式0容量被`capacity or default`恢复成250；Q3与Q4现已尊重字段来源标记。
2. 日期跨界时重复当天08–09窗口，而未读取次日是否开放；已改用`capacity_on_service_day`。相邻开门日期的跨夜窗若重叠，当前代码报错，要求给出人员/吞吐率规则，防止双算资源。

执行：`python -m pytest tests/test_takeover_core.py -q`，7项通过；`python -m pytest tests/test_q4_takeover.py tests/test_q4_v3.py tests/test_review5_fixes.py::TestQ4V4 -q`，17项通过。第三方pytest插件有一条未来版本弃用提示，没有测试失败。
