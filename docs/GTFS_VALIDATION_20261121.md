# 交通补全：从站点/距离代理到有日期的班次旅程

本轮完成了实际GTFS路由子模块，而非继续把“最近公交站”称为公交OD。作者为Codex交通子代理；代码/数据/数学验证与实地乘车验证分开列示。开发数值须在主代理冻结源代码后重跑，以最终`run_meta.json`为准。

## 1．原始数据与使用范围

使用仓库已经保存的City of Phoenix / Valley Metro夏季归档`mdb-147-202606160033.zip`，原字节SHA256为`d8d421ce9b5667024ae32d6428d8546074d7d35e2819a1b5ef689cc7c6cc38f6`。发布有效期为2026-04-27—07-26，参考服务日固定2026-07-20，America/Phoenix时区。另一包自7月27日才有效，不混用或重复叠加。原件来源、获取记录和生产端点见`资料/02_降温网络/GTFS/manifest_gtfs.json`；归档直链：[MobilityData原包](https://files.mobilitydatabase.org/mdb-147/mdb-147-202606160033/mdb-147-202606160033.zip)。这是历史发布计划表，不是2027年预测或实测车辆到达记录。

7月20日从`calendar_dates.txt`得到20个有效service、7,762条trip记录。没有`calendar.txt`符合GTFS。有效stop_times中1,094行达到/超过24小时，330,566行被发布者标成近似/插值时刻，47行不允许普通上车。数据只有4条机场跨站换乘规则，均要求至少300秒。2个SkyTrain trip模板有4行频率区间，`exact_times`为空，表示非固定相位服务；不能把模板只当一天一次班车，也不能擅自生成“准确09:00发车”。

规范依据为[GTFS Schedule Reference](https://gtfs.org/documentation/schedule/reference/)，2026-11-21打开核验。`calendar_dates`允许逐日列服务；跨午夜时刻保留24以上小时；非exact频率不等于固定时刻表；换乘表中的最短时间为总换乘时间；上/下车权限分别限制。这里是对官方规范的概述，完整数据字典以规范为准。

## 2．推导、算法和初边条件

令出发时刻为当地服务日起秒数s，目的地为j。旅程拆成接入步行、等待、乘车、换乘和末段步行，所有时间均为秒。每次乘车必须来自同日有效trip、允许上车/下车的stop_sequence区间。对某个固定trip的可登车时刻d，只有到达站台的时刻a≤d才可登车；落地时刻读取该trip后续发布arrival_time。

以登车次数k分层：A_k(v)是恰好乘坐k辆车后，在站v允许下车的最早时刻。A_0由起点接入步行得到。每层先由上层A_(k−1)建立站台就绪时刻，再扫描全部有效trip，枚举首次可登车位置并向后传播下车时刻。固定trip已在车上的乘客不受中间站“不上客”限制。到达较早的同站同层标签支配较晚者，因为允许等车且当前仅支持不依赖来车route/trip的换乘规则。

换乘就绪时刻为`arrival + max(步行耗时, 来源min_transfer_time)`；没有显式最短时间时用`max(步行耗时, 120秒工作缓冲)`。最短换乘时间不重复加在同一段步行上。禁止换乘的有向站对不生成该边。只允许一次生成的站间步行，不用多个中间站的步行链绕开禁止规则。目的地最早时刻取各层下车时刻加末段步行，与直接步行的较小值。

station层规则展开到child时，显式child端点更多的规则优先；同等具体程度的规则若矛盾则报错，CSV行顺序不决定权限。生成站间步行的0.5km上限是**每次换乘的总代理步行上限**，不是可以无限串联的每条边上限；显式来源换乘连接另行保留并按实际代理步行时间与来源最少时间的较大值计算。

默认最多3次登车（至多2次换乘），搜索出发后240分钟；初始无登车、起点接入已就绪。不满足界限的公交旅程不进入该次搜索，直接步行始终保留。这里的“最早”只指给定登车上限、搜索时限和步行连接集合内，不声称全城任意转车的无界最短路。30分钟阈值远小于240分钟；超过240分钟的遗漏不会制造额外30分钟可达边，但超过3次登车或受限接驳步行的遗漏仍可能影响可达分类。

固定班次和`exact_times=1`频率压缩班次在该有限行动集内按发布时刻求最早到达，后者按start/end/headway展开。`exact_times=0`的默认政策为`headway_bound`：在服务窗口内，假设普通乘客最多再等一个headway，再沿模板运行时间推算下车；接近窗口结束且无法保证剩余一班时不允许该次登车。这个等待上界是额外运营假设，发布者“尽力维持间隔”不保证现实等候真有上界。可选`exclude_nonexact`明确排除这些班次并记录数量，或`error`拒绝运行。输出逐段标`headway_bound_ride`，不混称发布的固定发车时刻。

## 3．工作假设与拒绝范围

| 假设/限制 | 必要性及代价 | 实现与失效后动作 |
|---|---|---|
| 接入/末段/换乘步行=球面距离×1.35÷4.8km/h | 缺真实人行路网和人群速度；不能给出无障碍/高温下可走性保证 | `Timetable.walk_seconds`；补真实路网与慢速人群后重新计算，不改称实测 |
| 接入、末段步行上限1.2km，生成站间步行上限0.5km | 控制不合理长接驳；会排除部分现实可走旅程 | 所有参数随metadata保存；应按群体能力做结构敏感性 |
| 默认换乘缓冲120秒 | 无逐站可靠性资料；保证不免费秒换乘 | 来源300秒要求优先，不重复叠加；实际拥挤/楼梯更慢时需要提高 |
| 原点为合成规划区代表位置 | 保持与旧模型同一需求位置，单独比较交通计算方法 | 不能把12点路径等同真实人口覆盖；人口加权多起点待有地址/空间数据后做 |
| 非exact频率采用最大一个headway等候 | 没有相位，不能造固定发车表 | 逐段标识，另可排除；不确定性仍是场景而非观测误差 |
| 有限登车与时限 | 给出可计算、可解释的旅行范围 | 缺省3/240可配置；结果明确记界限，建议用提高登车上限检验稳定性 |
| 不处理需要预约、协调上车的服务 | 普通未预约乘客不应被默认允许乘坐 | pickup/dropoff为2/3的相应上下车被排除；已在车中可通过中间禁止站 |
| 日期与字段必须可解释 | 避免“能跑但科学含义错” | 超feed有效期、缺时刻、非单一Phoenix时区、连续/预约窗口、route/trip特定换乘、timed/in-seat换乘类型均明确报错，未静默忽略 |

本feed没有触发不支持的复杂换乘或缺时刻，所以全部有效普通班次可进入已声明范围。无站点真实配员、拥挤、车厢制冷/座位、临时停运和实时延误，因此不能给出实际可达性、热暴露安全性或健康获益保证。

此外，当前没有利用`block_id`推断不同trip之间的同车续乘；即使物理车辆相同，跨trip仍按普通换乘计数/缓冲，故可能保守排除有利的免换车旅程。没有重建站内pathways、楼梯/电梯、无障碍条件或真实人行路网。也没有自动合并**前一service日**24点以后尚在运行的班次；传`25:xx`只表示所选service日的次日凌晨，而不是把自然日01点自动关联到前日。此feed当前参考日09/13/17查询晚于前日末班(原始普通表最大约26:17)，不因此遗漏前日普通班次；若研究凌晨、其他feed或特殊频率运行范围，须纳入前后service日再比较，不能直接沿用。固定班次最早到达只针对本程序已经声明的有界trip模型，不是GTFS全部语义或现实全网全局最优。

## 4．验证层次与结果

`tests/test_gtfs_routing.py`有18项专门检查：独立小时间表上的已知最早到达、逐日加入/删除例外、25点时刻、四种上下车约束、换乘缓冲、300秒跨站最小时间、禁止换乘、固定频率展开、非固定频率三种显式政策与窗口结束、feed范围、直接步行备选、搜索界限、不支持的特定trip换乘明确报错、child覆盖parent不依行顺序及同等具体程度冲突拒绝。它们能证伪时钟/权限/换乘实现错误，不代表现实公交表现已验证。

参考日按09:00、13:00、17:00三个出发时刻，12个代表区到24个室内站点+8个候选点生成1,152条OD。535条选用公交，3条含明确标注的headway-bound段。排班路由与旧距离速度代理的30分钟分类有39格不同；两种方法差的中位数48.333分钟。这个“差”是两个模型间的结构差异，不是相对实测真值的误差。

保持MAG站点、候选点、需求、时段、容量和30分钟阈值不变，只替换access矩阵：p=3时距离速度代理缺口212.768人次、选MCH-3/4/8；09或13点排班路径缺口278.875、选MCH-3/4/6；17点缺口269.749、同选3/4/6。三时点中位矩阵与最坏矩阵在本样本也选3/4/6。**这足以推翻“交通代理不影响推荐”的说法，但不支持把排班结果称为真实覆盖率。** 三个时刻的分位仅是采样时刻摘要，不是出行时间概率分布或统计置信区间；一天只用一个出发时刻矩阵做LP对照也是结构实验，不代表所有访客在同一时刻出发。

`independent_source_leg_audits.json`从原zip重新读取8个选中旅程（先覆盖有公交选路的7个不同原点，再补一条），分别核实际trip、上下车站、发布字符串时刻和权限，并独立加总接入、等候、乘车、换乘和末段，端到端时间收支残差为0。另`source_trip_hand_examples.json`保留68CM 06:01→06:34的33分钟原始trip、一个跨24点trip及SkyTrain频率模板的人工式算例。它们验证旅程能追到原始发布数据，不是站点实际运营的独立观测。

## 5．复算与建模接口

```text
python -m pytest tests/test_gtfs_routing.py -q
python -m src.exp.run_gtfs_validation --out results/complete_20261121/gtfs
python -m src.exp.run_gtfs_validation --city-operations --out results/complete_20261121/gtfs_city_operations
```

默认从原仓库路径读取已归档zip，metadata包含完整SHA256及日期、频率政策、步行/缓冲/搜索参数。完整输出为`od_by_departure.csv`、`itineraries.json`、`sampled_departure_summary.csv`、`matched_inventory_siting.csv`、两个审计JSON、summary与run_meta。按`district_id/site_id/departure`可复算任意格。

`--city-operations`显式叠加主模型的城市运营层（例如MAG登记之外的respite站点），应写入独立结果目录；不能覆盖原32目的地的MAG-only对照，或把“增加设施”造成的变化全部归因于路由算法。每个目录内的proxy/GTFS对照仍共用同一设施层。

加入城市运营修正层后为12×34×3=1,224条，574条选择公交、3条涉及headway-bound，44格30分钟分类改变，全矩阵模型间差中位43.229分钟。同层p3距离速度代理缺口197.373，09/13点GTFS缺口278.875、17点258.899，选址仍从3/4/8改变为3/4/6。该层新增容量和点坐标的证据/假设由主模型运营修正表独立标注，不能因此将需求与实际出行验证判为通过。

`frequency_policy_sensitivity.json`只重查受非exact频率影响的旅程，将其改为显式排除后比较；未使用频率段的原最优路径仍然可行，故无须把其余格当作新增随机样本重复计算。`routing_structure.png/pdf`直接来自本目录OD与同输入p3表；左图是两算法的散点对照、右图是条件缺口，均非观测误差/现场覆盖验证。

核心API为`Timetable(archive,date).route(origin,{site_id:(lat,lon)},departure,max_boardings=3,horizon_minutes=240)`。本轮没有静默覆盖旧`realnet`默认交通表；若主模型使用某个出发时刻、中位或最坏矩阵，必须在配置中明确指定，固定与候选点保持同一算法。若要逐时需求模型，应按该时段出发时刻分别调用路由，而不是不加说明地把一天一个矩阵叫逐时门到门真值。

因此“GTFS排班接入未实现”的技术缺口已补；“实际乘车时间验证、步行路网/高温人群速度、真实人口位置”等科学缺口仍保留，需要独立资料，不以完成代码或0收支残差代替。
